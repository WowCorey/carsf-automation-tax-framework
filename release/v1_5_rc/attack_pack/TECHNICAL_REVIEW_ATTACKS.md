# Technical Review Attacks

This attack document does not mean external review has been completed, does not mean approval has been granted, and does not mean validation has occurred. It is not legal advice, not tax advice, not ATO guidance, not Treasury modelling, not economic validation, not welfare validation, not statistical validation, not compliance scoring, not enforcement, and does not modify firm-level CARSF liability.

## What To Inspect First

- `.github/workflows/ci.yml`
- `data/release/v1_5_release_manifest.yaml`
- `data/dashboard/executive_dashboard_manifest.yaml`
- `reports/repo_guardrails.md`

## Attack Questions

- Does CI run every report runner in dependency order?
- Do missing reports and missing layers fail closed?
- Are documentation allowlists too broad?
- Do Markdown reports match JSON payloads?
- Are generated artefacts stale against manifests?

## Likely Failure Modes

- A runner is absent from CI.
- A manifest references a stale path.
- A report exists but is not regenerated by acceptance commands.
- Guardrail allowlists hide sensitive-marker misuse.
- Tests cover success paths without mutation failures.

## Required Evidence / External Review

- CI run log.
- Manifest trace.
- Runner reproduction log.
- Guardrail fixture review.
- Fail-closed mutation test review.

## What Not To Infer

- Do not infer technical validation, security adequacy, DLP completeness, approval, readiness, or firm-level liability change.

## Locked-Until-Review Items

- CI coverage completeness.
- Manifest drift controls.
- Guardrail allowlists.
- Generated-report traceability.
- Fail-closed mutation coverage.

## Suggested Reviewer Output Format

List file, command, failure expectation, observed behavior, missing test, and required patch.
